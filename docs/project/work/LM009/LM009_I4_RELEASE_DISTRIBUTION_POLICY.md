# LM009-I4 — VS Code extension release and distribution policy

Status: **RATIFIED — GitHub Release is the canonical public distribution path**

Allocated: **2026-09-14**

Primary consumer: `LM009-I4` / GitHub #474

Nature: governance-only editor distribution and release policy

Normative language effect: **none**

## Decision

LM009's packaged VSIX has one canonical public release path:

> **A GitHub Release attached to an explicit release tag is the canonical public
> distribution record for the Protos VS Code extension.**

GitHub Actions CI artifacts remain validation/intermediate artifacts. They are
not the durable public release identity.

Marketplace and Open VSX publication are **optional downstream distribution
mirrors**. They are deliberately not required for LM009 closure, and no
automatic publication to either registry is authorized by this record.

## Release identity

The extension package has an **independent extension version** governed by its
own SemVer sequence.

The Protos runtime/language implementation version is a separate versioning
authority.

A release may pair a specific extension version with a compatible runtime
range/documented minimum, but the VSIX version is not mechanically derived from
the Java/runtime version.

This preserves the thin-client boundary:

```text
VS Code extension version
    !=
Protos runtime version
```

The extension continues to resolve the external `protos.runtime.executable`
launcher for Run, Debug and language-server startup.

## Canonical release artifact

The release VSIX must be byte-identical to the canonical I2/I3 packaging
procedure for the release commit.

Release evidence must include:

```text
release_tag
extension_version
source_commit
canonical_vsix_sha256
```

The generated VSIX is attached to the GitHub Release. It is not committed to
the source repository.

The SHA-256 sidecar generated by CI is retained as release evidence.

## Release trigger

A public extension release is an **explicit release action**, not a side effect
of ordinary `main` pushes.

The canonical sequence is:

```text
main
  ↓
CI packaging + clean-install/debug evidence
  ↓
explicit release tag
  ↓
GitHub Release
  ↓
canonical VSIX attached
```

Ordinary development pushes may produce CI artifacts but must not publish a
public release.

## Registry mirrors

Marketplace and Open VSX are intentionally classified as mirrors.

They may be added later without changing the canonical artifact identity:

```text
GitHub Release
    ↓
canonical VSIX
    ├── optional Marketplace publication
    └── optional Open VSX publication
```

A registry publication must consume the already-canonical VSIX/release identity.
It must not rebuild a semantically equivalent but independently generated VSIX.

No registry credentials belong in the repository.

No registry publication happens automatically on ordinary `main` activity.

## Runtime coordination

The release contract does not bundle the Protos runtime, Java runtime, language
server implementation, or JAR/classpath payload into the VSIX.

The editor remains a thin workspace extension and continues to use:

```text
protos.runtime.executable
```

as the external authority.

Runtime compatibility information may be documented in release notes, but
runtime distribution remains a separate release concern.

## Rollback and supersession

A published GitHub Release is immutable as a historical record.

Corrections are represented by a new extension version and a new release tag.
A replacement release never mutates the identity of a previous release.

CI artifacts from `main` remain validation artifacts and are not retroactively
promoted by filename alone.

## Security and supply-chain boundary

The public release must originate from the canonical CI packaging path and carry
the same content/reproducibility guarantees established by D128 C″.

The release process must not:

- download runtime dependencies at extension activation;
- add Protos runtime payload to the VSIX;
- publish from an unclean development tree;
- silently rebuild the artifact outside the canonical packaging path; or
- require repository/package credentials to install the released extension.

## LM009 closure consequence

With this policy, the LM009 closure contract is:

```text
PUBLIC_RELEASE_PATH_EXPLICIT=YES
PUBLIC_RELEASE_CANONICAL_PATH=GITHUB_RELEASE
EXTENSION_VERSION_POLICY=INDEPENDENT_SEMVER
RUNTIME_VERSION_POLICY=SEPARATE
CI_ARTIFACT_IS_PUBLIC_RELEASE=NO
MARKETPLACE_REQUIRED_FOR_LM009=NO
OPEN_VSX_REQUIRED_FOR_LM009=NO
PUBLIC_REGISTRY_AUTO_PUBLISH=NO
CANONICAL_VSIX_ATTACHED_TO_RELEASE=YES
GENERATED_VSIX_COMMITTED=NO
```

Marketplace/Open VSX integration may become a later family/slice without
reopening the LM009 packaging identity.

## Non-effects

This policy does not alter:

- Protos language semantics;
- runtime/debugger behavior;
- the D127 dependency/runtime boundary;
- D128 canonical artifact identity;
- I2 CI artifact production;
- I3 clean-install, Run or Debug evidence;
- the existing extension API or LSP/DAP protocol contracts.
