## 1. Purpose and evidence boundary

This record retains the exact Protos-side evidence produced while experimentally
validating Oracle/Graal PR #14434 against a disposable Protos adaptation.

The experiment answered a future-looking question: if Protos later has the
Bytecode DSL/C′ continuation infrastructure required by the already-ratified
control/unwind architecture, can Truffle's configurable Bytecode DSL unwind
exceptions carry Protos non-local return and cancellation directly through
structured cleanup without the temporary guest-exception wrapper/interceptor
transport?

The result was strongly positive semantically and mixed but informative for
optimizer behavior.

This document is evidence, not implementation authority. In particular:

- current production Protos does not have the experimental substrate used here;
- no dependency upgrade is authorized;
- no migration to an unreleased Graal/Truffle artifact is authorized;
- no Protos semantics are changed or redefined;
- PLAT021 is not reopened or amended by this evidence;
- PERF006 is not extended by this evidence and gains no dependency on it;
- optimizer findings are retained as observations, not attributed to PR #14434
  without causal evidence.

## 4. Protos selected unwind exceptions

The disposable generated Protos Bytecode root configured exactly two internal
control transfers:

```java
@GenerateBytecode(
    languageClass = ProtosLanguage.class,
    enableYield = true,
    enableTagInstrumentation = true,
    enableRootTagging = false,
    enableRootBodyTagging = false,
    tagTreeNodeLibrary = ProtosBytecodeTagTreeNodeExports.class,
    unwindExceptions = {
        ProtosNonLocalReturnException.class,
        ProtosTaskCancellationException.class
    })
```

Both selected classes extend `ControlFlowException`.

Guest Error remained deliberately separate:

```text
ProtosSignalException extends AbstractTruffleException
```

`ProtosSignalException` was not added to `unwindExceptions`.

This separation was a central invariant of the experiment:

```text
internal NLR / cancellation
    -> configured ControlFlowException unwind lane

guest Error
    -> existing AbstractTruffleException guest-error lane
```

## 5. Experimental bridge removal

The purpose of the experiment was not merely to add the annotation while leaving
the old transport active. That would not prove that direct configured unwind was
actually sufficient.

The disposable adaptation therefore removed the previous wrapper/interceptor
transport:

```text
ProtosBytecodeControlTransferException extends AbstractTruffleException
```

and removed the custom control-flow interception used to wrap NLR/cancellation
for structured cleanup.

Relevant B4A evidence:

```text
PERF006_B4A_DIRECT_NLR_IDENTITY=PASS
PERF006_B4A_DIRECT_CANCELLATION_IDENTITY=PASS
PERF006_B4A_FOREIGN_CONTROL_WRAPPED=NO
PERF006_B4A_CUSTOM_CONTROL_INTERCEPTOR=NO
PERF006_B4A_CONTROL_TRANSFER_WRAPPER=REMOVED
```

The owner-boundary helper was changed to accept direct `ControlFlowException`
transport:

```java
Object handleControlTransfer(ControlFlowException transfer) {
    if (moduleInitialization != null) {
        moduleInitialization.fail();
        throw transfer;
    }
    if (transfer instanceof ProtosNonLocalReturnException nonLocalReturn
            && ownsReturnHome
            && returnHome.isActive()
            && nonLocalReturn.target() == returnHome) {
        return nonLocalReturn.value();
    }
    throw transfer;
}
```

Call/resume ownership boundaries caught `ControlFlowException` directly and
delegated to the owning prepared call.

## 6. Important ownership regression found and corrected

The first full wrapper-free semantic run exposed two raw non-local-return errors
in Test Tool paths.

This did not show a failure of PR #14434. The experimental bridge-removal pass
had accidentally removed a semantic ownership boundary in
`ProtosBytecodeTaskExecution.runPreparedSegment(...)`, treating it as though it
were only wrapper plumbing.

Restoring that boundary with direct `ControlFlowException` ownership handling
fixed the regression without restoring the wrapper transport.

The corrected experimental boundary preserved:

- ReturnHome ownership;
- Task cancellation completion/unwind ownership;
- direct `ControlFlowException` transport;
- no guest-exception envelope.

This distinction is important future evidence: some old bridge-adjacent catches
were semantic ownership boundaries and must not be deleted merely because wrapper
transport becomes unnecessary.

## 8. Exact cancellation + suspending-cleanup stress case

A dedicated hot harness repeated the difficult cancellation/ensure scenario 500

```text

    -> Task dispatch resumes unwind
    -> pending ProtosTaskCancellationException crosses ensure
```

## 10. Optimizer investigation — VirtualFrame capture

Aggressive compilation tracing first exposed:

```text
FrameWithoutBoxing should not be materialized
```

The path led to `ProtosLookupNode.executeDirect(...)`.

The original disposable source obtained the activation into a local `context`
but captured the `VirtualFrame` again inside the exception-supplier lambda:

```java
ProtosActivation context = ProtosFrameArguments.activation(frame);
return context.lookup(name)
        .orElseThrow(
                () -> new ProtosSignalException(
                        ProtosCoreErrors.newUnqualifiedLookupError(
                                ProtosFrameArguments.activation(frame))));
```

The experimental mechanical correction reused the already-derived activation:

```java
ProtosActivation context = ProtosFrameArguments.activation(frame);
return context.lookup(name)
        .orElseThrow(
                () -> new ProtosSignalException(
                        ProtosCoreErrors.newUnqualifiedLookupError(context)));
```

The bailout disappeared.

This finding was classified as Protos optimizer hygiene, independent of the
unwind API semantics. The fix existed only in the disposable clone and this
evidence does not itself authorize a production patch.

## 11. Optimizer investigation — `Too deep inlining`

A second optimizer finding was:

```text
PermanentBailoutException:
Too deep inlining, probably caused by recursive inlining.
```

It was first seen under `CompileImmediately`, which by itself would have been
insufficient evidence for a production-path concern.

Later warmed harnesses reproduced the problem without `CompileImmediately`, so
the earlier provisional "stress-only" interpretation was rejected.

Examples included generated paths involving:

```text
ProtosBytecodeRootNodeGen$CachedBytecodeNode.handlePrepareSendArguments_
ProtosBytecodeRootNodeGen$CachedBytecodeNode.continueAt
ProtosBytecodeRootNodeGen.execute
```

and, for the cleanup resume target:

```text
ContinuationRootNodeImpl.execute
    -> generated continueAt
    -> handlePrepareClosureCall_
```

Important evidence boundary:

- the bailout is real in the tested Protos/Truffle combination;
- semantics remained correct;
- no experiment established that PR #14434 causes the bailout;
- no arbitrary inlining workaround was applied.


Its source position was:

```text
OptimizedCallTarget.doInvoke
OptimizedCallTarget.callDirect
OptimizedDirectCallNode.call

ProtosBytecodeRootNodeGen$CachedBytecodeNode.handleResumeContinuation_
ProtosBytecodeRootNodeGen$CachedBytecodeNode.continueAt

```

The corresponding Protos specialization was:

```java
@Specialization(
        guards = "result.getContinuationRootNode() == cachedRoot",
        limit = "3")
public static Object direct(
        PreparedClosureCall prepared,
        ContinuationResult result,
        Object resumeValue,
        @Cached("result.getContinuationRootNode()")
                ContinuationRootNode cachedRoot,
        @Cached("create(cachedRoot.getCallTarget())")
                DirectCallNode node) {
    try {
        return node.call(
                result.getFrame(),
                resumeValue);
    ...
}
```

Therefore the residual `callBoundary` is specifically the cached continuation
root target, not an unrelated guest call.

Conclusion:

```text
hot no-suspend root:       FULLY INLINED / ABSORBED
Future.value resume:       FULLY INTEGRATED
post-cleanup top resume:   NOT FULLY INLINED
cleanup own resume:        no final graph; Too deep inlining bailout
```

This is useful optimizer evidence but not evidence that PR #14434 caused the
residual boundary.

## 18. What this experiment established

The strongest supported conclusion is:

> On the disposable Bytecode DSL/C′ substrate tested, Truffle's configurable
> unwind-exception mechanism can carry Protos internal non-local return and
> cancellation directly as `ControlFlowException` through structured cleanup,
> including cleanup that suspends/resumes, while preserving guest Error
> separation and the existing ownership/supersession semantics.

It also established that the old experimental wrapper/interceptor transport is
not intrinsically required by those semantics on the tested PR.

## 19. What this experiment did not establish

The experiment does **not** establish any of the following:

1. that current production Protos can adopt the mechanism now;
2. that Protos should upgrade to a particular GraalVM/Truffle release;
3. that the unreleased PR API is stable until it appears in a supported release;
4. that removing the wrapper from future production code is mechanically safe
   without revalidating the then-current implementation;
5. that PR #14434 causes `Too deep inlining`;
6. that PR #14434 causes the residual continuation `callBoundary`;
7. that the inspected graphs prove an application-level performance speedup;
8. that the temporary POM/runtime alignment is the correct production dependency
   model;
9. that the temporary `ProtosLookupNode` optimizer-hygiene correction is
   authorized production work;
10. that any new Protos semantic/platform decision has been ratified by this
    evidence.
